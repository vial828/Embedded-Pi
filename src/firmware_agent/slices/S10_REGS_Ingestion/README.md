## 已实现：PIN_MAP（`pinmap.py`）

读客户给的 IO mapping xlsx（标准库解压 + 解析 XML，不依赖 openpyxl），按表头文字定位列，
每张器件表独立成组，每行带出处坐标（文件 / sheet / 行号）。

```python
table = PinMap.load(".../Adonis-1P 1.5_IO-Mapping_V2.1_20251210.xlsx")
table.find("SPI")        # 8 行：LCD 的 SPI 在 P7.0-7.3，FLASH 的在 P11.x
table.by_pin("P7.3")     # 脚号和封装球号都能查（E3 == P7.3）
table.find("IMU")        # 0 行，并说明在哪些行里找的
```

三条纪律：

1. **列按表头文字找**，不按位置。硬件同事插一列，位置读取会把"Pin type"当成网络名，
   而且不会报错。
2. **一个脚有两个名字**（封装球号 `E3` / 默认端口名 `P7.3`），两个都要能查。只支持前者
   会让每个真实提问都返回空——数据在，答案说没有，这是最坏的失败。
3. **空结果必须自证**。"表里说没有"和"表没法说"是两回事，混起来就是一个外设悄悄从提示词
   里消失。所以查询结果带：搜了多少行、来自哪几张器件表、哪些表被跳过及原因，并且明写
   "这是查询无结果，不是硬件确认不存在"。

## 未实现：BOM / 网络表

"某个网络的另一头是哪颗芯片、什么型号"——IO 表里没有这个信息，只有 MCU 这一侧。
而"拿型号去已提供的文档里匹配 spec"这一跳依赖型号，所以现在**不是断链，是没有这个数据**。

已确认走导出路线：由硬件从 Altium 导出 **BOM + 网络表 CSV**（纯文本、零解析风险）。

SCH 本身读不了：SchDoc 是 OLE 复合文件，Altium 记录标记 `Record=` 在三个文件里出现 0 次
（ASCII 与 UTF-16 都试过），文本是压缩存在流里的。不打算硬解——资料要给人能读的形态。
