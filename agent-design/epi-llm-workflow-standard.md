# EPI LLM 使用标准流（作用域 / 用前 / 用中 / 用后）

> 状态：设计定稿待评审
> 适用：文档工作流中**所有** LLM 调用点，不仅 PRD
> 前置结论：**不做格式 adapter 集**。格式差异由 LLM 归一化吸收，正则只服务唯一目标格式

## 0. 总纲

> **LLM 只负责把任意输入归一化成唯一的标准格式文档；正则负责把标准格式变成 JSON；
> 正确性由「字源双向映射」证明，而不是由 LLM 保证。**

三条推论：

1. **LLM 不产 JSON**，产带锚点的标准格式文档 —— JSON 里的字符串一旦脱离锚点就无法回比
2. **正则固定且普适** —— 只认一种格式；格式变更必须同步改正则 + 改测试
3. **不承诺 LLM 正确** —— 只承诺偏差必然被某层暴露，暴露不了的留下完整证据链

## 1. 唯一货币：字源锚点

唯一能被代码机械验证的东西是**原文字符区间**。所有审计最终归结为它：

| 要防的 | 归结为 |
|---|---|
| 改写 | `origin: source` 字段，其锚点区间切片必须逐字相等 |
| 遗漏 | 原文每个非空白字符必须被 ≥1 条条目锚定 |
| 发挥 | `origin: generated` 字段必须显式 `basis: <区间>` 或 `basis: null` |
| 曲解 | 左右审计必须引用左侧锚点作判据，禁止空口评价 |

## 2. 作用域矩阵

一次调用只能归入一类动作，**禁止混态**（混态导致无法归因"这句是抄的还是编的"）：

| 动作 | 允许 | 禁止 | 证明方式 |
|---|---|---|---|
| **搬运 carry** | 指认原文区间、贴标签 | 改任何字符、合并两句、吞掉限定语 | 逐字回比 + 覆盖率 |
| **补全 elaborate** | 生成原文没有的内容（AC、假设、拆分建议） | 混进搬运字段、不声明出身 | `origin`/`basis`/`assumptions`/`invented_values` 四件套 |
| **判断 judge** | 分类、打分、左右审计裁决 | 输出正文、输出解释性长文 | 结论必须带证据锚点 |

### 各环节落位

| 环节 | 动作 | LLM | 审计等级 |
|---|---|---|---|
| S08 规范入库 | 搬运 + 判断 | 可用 | 中 |
| **S09 PRD 入库** | 搬运 + 补全 | 可用 | **最高**（需求是唯一真值源） |
| S10 寄存器入库 | **仅搬运** | 可用 | 最高，**禁止补全任何数值** |
| S04 系统设计生成 | 补全 + 判断 | 可用 | 最高 + 人签字 |
| S14 记忆候选提名 | 判断 | 可用 | 中 |
| S15 晋升判定 | — | **禁止** | 规则引擎 |
| S17 上下文组装 | — | **禁止** | 确定性 |
| S11 artifact graph | — | **禁止** | 纯代码 |
| S20+ 代码生成 | 生成 | 可用 | 由编译器/测试审计，不靠 LLM 自证 |

规律：**越靠近事实（原文、寄存器、数值）越禁止生成；越靠近决策（架构、拆分）越允许生成，但审计越重且必须人签字。**

## 3. 三段闸门

### 3.1 用前准备（Pre）

| 项 | 内容 | 不做的后果 |
|---|---|---|
| 任务分级 | `动作类型 × 安全等级` → 审计强度矩阵 | 一刀切：要么过审要么裸奔 |
| 输入锚定 | 抽取 + 字符偏移编号 + 分块（块 id + 块 hash） | LLM 无法回传锚点，全部审计失效 |
| 输出格式冻结 | 唯一标准格式模板（§4），与正则配对 | 格式漂移 = 正则失效 = 静默漏 |
| 提示词版本化 | prompt 进 git，`prompt_sha256` 进产物 | 无法解释"上次能跑这次不能" |
| 幂等键 | `sha256(输入 + prompt_sha + model + schema_ver)` | 重复调用、结果不可复现 |
| 失败预算 | 预先定义失败判据（覆盖率阈值、疑点条数） | 事后讨价还价 |
| 基线快照 | 记录输入 hash，供增量与回归 | 每次全量重跑 |

### 3.2 用中规范（During）

| 规则 | 说明 |
|---|---|
| 单任务单职责 | 一次调用只做搬运 / 补全 / 判断中的一类 |
| 强制锚点 | 搬运字段无锚点 = 无效，直接拒收 |
| 生成必须留名 | `origin: generated` + `assumptions[]` + `invented_values[]` |
| 自拟数值单独标红 | 原文数字多重集里没有的数值 → `invented_value`（零误判） |
| 禁止自由叙述 | 输出不得含解释性文字；解释放独立字段 |
| 确定性参数 | `temperature=0`、固定 seed、结构化输出 |
| 分块 + 重叠窗口 | 长文档可续跑、可增量、可定位 |
| 幂等 | 同输入同输出；命中缓存则不调用 |

### 3.3 用后审计（Post）—— 便宜在前，昂贵在后

| 层 | 执行者 | 检查 | 不过则 |
|---|---|---|---|
| **L0 格式** | 代码 | 正则可解析、schema 合法、锚点在范围内 | 拒收整批 |
| **L1 字源映射** | 代码 | 正向：原文非空白字符 100% 被锚定（防漏）<br>反向：`source` 字段逐字相等（防曲解）<br>`generated` 字段必须有 basis 声明（防发挥） | 拒收 + 打印悬空区间 |
| **L2 守恒** | 代码 | 数字+单位 token 多重集对账<br>情态/否定词计数对账 | 阻断相关条目 |
| **L3 左右审计** | LLM（**不同厂商模型**） | 逐条：左=原文片段+锚点，右=index 条目<br>结论 ∈ `faithful / missing / distorted / invented / unresolved`<br>必须引用左侧锚点作证据 | `distorted` / `missing` 阻断该条 |
| **L4 人工复核** | 人 | **只复核 L1–L3 标出的疑点 + 全部安全相关条目**（非全量） | 阻断该条 |
| **L5 客户确认** | 客户 | 按章节的**覆盖地图** + 噪声声明，逐条 ✓/✗/改 | 需求完整性唯一真值 |

L5 的问法很关键：**永远不要问"有没有漏"**（人答不了）。要问：
「这是我从您 §3.2 抽的 11 条；这 3 句我当成说明文字跳过了，对吗？」

## 4. 唯一标准格式（正则目标）

行首标签固定、锚点语法固定，因此**一套正则普适**：

```text
@REQ   R-001
@SRC   1240..1279
@TITLE [gen->1243..1248] BLE App Control & OTA
@ATOM  [1243..1248] BLE功能
@QUAL  [1240..1243] 需要有
@ATOM  [1251..1272] 跟手机app连接实现app control
@ATOM  [1273..1278] OTA升级
@FLAG  open_ended [1278..1279] 等
@AC    [gen] 设备作为 BLE Peripheral 广播，App 通过 GAP 完成配对与连接
@AC    [gen->1251..1272] App 通过 GATT 写控制特征值
@ASSUME GAP 协议；角色=Peripheral
@VALUE? 100ms
@NOISE page_header [0..40]
```

| 语法 | 含义 | 校验 |
|---|---|---|
| `[a..b]` | 原文锚点 | `doc[a:b]` 必须等于本行正文 |
| `[gen]` | 生成内容，无原文依据 | 必须配套 `@ASSUME` 或 `@VALUE?` |
| `[gen->a..b]` | 生成内容，依据在锚点 | 依据区间必须存在 |
| `@VALUE?` | 自拟数值 | 原文数字多重集里没有 → 必须客户确认 |
| `@FLAG open_ended` | 开放枚举（"等"、"等等"、"诸如此类"） | **阻断**：该 REQ 客户确认前不得进设计输入 |

### 样例：客户一句话 → 三条需求 + 一个红旗

原文：`需要有BLE功能能支持跟手机app连接实现app control、OTA升级等`

| atom | quote（逐字） | src | qualifier |
|---|---|---|---|
| A-001a | `BLE功能` | [1243,1248) | `需要有` [1240,1243) |
| A-001b | `跟手机app连接实现app control` | [1251,1272) | `能支持` [1248,1251) |
| A-001c | `OTA升级` | [1273,1278) | — |
| 红旗 | `等` | [1278,1279) | open_ended：枚举未穷尽 |

守恒：所有 quote ∪ qualifier ∪ 分隔符 ∪ noise == 全部非空白字符，互不重叠。
**`等` 是整套流程最值钱的产出** —— 它证明客户自己承认需求没写完，正确动作是生成澄清项，不是让模型补全。

## 5. 审计包（每次 LLM 任务一个目录，全部入库）

```text
Docs/ai-generation/audit/<task-id>/
  task.json            契约：动作类型/安全分级/prompt_sha/model/输入 hash
  input.numbered.txt   带锚点的输入
  output.raw           模型原始输出（不可改）
  output.std.md        标准格式文档（人 review 的对象）
  mapping.json         字源双向映射表
  audit.l0-l2.json     代码审计结论
  audit.l3.json        LLM 左右审计（逐条 verdict + 证据锚点）
  review.json          人工复核结论
  acceptance.json      客户确认（按章节）
  status.json          accepted / partial / rejected
```

**下游只允许读 `status=accepted` 的条目。**

## 6. 六条硬规则

1. LLM 不产 JSON，产标准格式文档
2. 字源是唯一货币 —— 一切审计归结为字符区间
3. 生成必须留名（origin / basis / assumptions / invented_values 四件套）
4. 审计分层：代码能查的不给 LLM 查，LLM 能查的不给人查
5. 不确定就阻断，不猜测（进 pending，不进 index）
6. 可复现优先：模型或 prompt 变更 = 全量重审计

## 7. 与「八步方案」的关系

八步是 **S09 一个环节的内部流水线**；本标准流是**所有 LLM 调用点共用的治理框架**。八步被吸收，不是被推翻：

| 八步 | 归宿 |
|---|---|
| 1 抽取 | 保留 → Pre「输入锚定」 |
| 2 标注（只给区间） | 保留 → 放宽为「搬运 + 补全」两类动作，产物是标准格式文档 |
| 3 拼装（代码切片） | 保留 → L1 反向逐字回比 |
| 4 覆盖率对账 | 保留 → L1 正向 100% 覆盖 |
| 5 数字守恒 | 保留 → L2 |
| 6 情态/否定守恒 | 保留 → L2 |
| 7 多轮一致性 | **降级为可选**：搬运类用一致率；补全类改用「共识度」（并集 + 频次），不要求一致 |
| 8 客户确认 | 保留 → L5，改为按章节覆盖地图 |
| （新增） | 作用域矩阵、Pre 三段、L0 格式审计、L3 左右审计、审计包 |

## 8. 待决问题

1. **L3 左右审计用哪家模型**：必须与产出模型不同厂商；成本按条目数计 —— 是否只对 `generated` 字段跑？
2. **标准格式的分块粒度**：按 REQ 分块？按原文页/章节分块？影响增量重跑范围与缓存命中率
3. **`@NOISE` 滥用上限**：噪声占比阈值（草案 25%）；超限是告警还是阻断？
4. **安全相关条目的判定规则**：靠关键词（充电/加热/RDP/寄存器/保护）还是人工预标章节范围？
5. **`requirements_index.json` 字段分层**：`source_text` 与 `proposed_acceptance` 同文件不同顶层键，还是拆两个文件（倾向拆）
6. **现有 ADO 正则路径的定位**：降级为「缓存优化」，还是改造成标准格式产出器给 L1–L3 当 fixture？

## 9. 建议实施顺序

1. 定稿 §4 标准格式 + 正则 + schema（**先评审后编码**）
2. 实现 L0/L1/L2 校验器（纯代码 + 单测，用现有 ADO PDF 当 fixture）
3. 把现有 ADO 正则改造成标准格式产出器 → 白捡覆盖率与守恒校验
4. 接 LLM 产出器（搬运 + 补全，两次独立调用）
5. 接 L3 左右审计 + L5 客户确认清单生成器
6. 回头补【质量门禁】（`PrdParseError` / `ParseReport`），作为 L0–L2 的统一出口
