## 一、起因与结论

**现象**：`epi` 跑过之后 `requirements_index.json` 变空，怀疑 PRD 解析代码丢了。

**真相（三条独立问题叠加）**：

1. **代码在另一台机器上** —— PRD 解析、workflow 实现在 Linux 机器（`vial@10.2.3.6:~/projects/Embedded-Pi`），Windows 侧落后。已通过
   `git fetch ssh://vial@10.2.3.6/home/vial/projects/Embedded-Pi feat/m0-bootstrap` 拉齐。
2. **裸跑 `epi` 会销毁生成物** —— `cli.py:83` 的 `ensure_project_layout()` 在 `cli.py:105` 的 `run_workflow()` **之前**执行；
   `Docs/ai-generation/**` 全部解析成 `SYNC_MANAGED`，于是每次运行都把生成物回写成空模板。
   更糟：状态机已过 `INGEST` 阶段，**不会重新解析** → 数据永久丢失。
   实测：`ingest 176 条 → 裸跑 epi → 0 条`。
3. **解析质量** —— ADO 导出的页脚回显（`User Story: X  Page 7 of 37`）被当成 story 头，
   既伪造重复条目又截断上一条的 acceptance criteria；另有 `please refer to User Story N` 占位条目重复计数，
   而它们**独占 Azure work-item ID**。

## 三、设计讨论定稿（见 `epi-llm-workflow-standard.md`）

关键决策链，按讨论顺序：

1. PRD 解析是**纯代码**（正则 + 状态机，零 LLM，sha256 可复现）—— 已实测确认
2. 但**格式脆弱**：10 个格式变异测试里 7 个静默归零、3 个静默丢内容、**0 个报错**；
   非 ADO 格式会走"每行一条需求"分支，产出**看起来正常的需求垃圾**并通过门禁
3. 曾提议「格式 adapter 集」→ **否决**：维护量 O(客户数 × 模板版本)，普适性为零，正则坟场
4. 曾提议「LLM 归一化」→ 修正为**独立可审计步骤**，且 **LLM 只交字符区间、不写正文**
5. 曾提议「LLM review」→ 顾虑（同源盲区 / 查不出缺失 / 零信息 LGTM / 数据即指令）→
   收敛为 **L3 逐条左右审计**（不同厂商模型 + 必须引用锚点证据）
6. 用户提出「切原文每一个字源去映射 LLM 生成的 index」→ 确立**字源是唯一货币**
7. 最终抽象：**LLM 产标准格式文档，正则产 JSON**，正则固定普适；治理框架适用于所有 LLM 调用点

被否决/降级的方案记录（避免以后重走）：

- ❌ 格式 adapter 集（主路径）→ 降级为可选缓存优化
- ❌ LLM 直接产 `requirements_index.json`
- ❌ LLM review 替代代码校验（只能叠加，不能替代）
- ⚠️ 多轮一致性 → 搬运类用一致率，补全类改用「共识度」（并集 + 频次）
